## What this is
ACSL (Attention-Coupled Security Loop) — a defensive safety-eval harness. It tests whether an internal security probe read at a mid-network attention layer beats output-level refusal under jailbreaks, on a frozen LLM. ## Verification (tiered — match the check to the stakes)
Verification effort is budgeted. Full fresh-agent passes cost 100–300K tokens; spend that only where an undetected error would poison a cited result or the trust chain. Every verification report must state which tier ran and which (device, dtype) profiles were actually executed.

**Tier 1 — full Independent Verification (fresh agent).** Required only for: (a) changes to load-bearing measurement code (`acsl/hooks.py`, `acsl/extract.py`, `acsl/head.py`, `acsl/directions.py`, `acsl/eval/`); (b) any code that writes result-bearing artifacts (activation caches, probe scores, paired-eval metrics); (c) any result-bearing claim before it is cited (see Rule 9). The verifier is a fresh agent with no conversation access, receives ONLY the acceptance criteria and the named files in scope (not "read the repo"), independently recomputes exactly ONE headline number from raw artifacts, and reports PASS/FAIL per criterion. Cap the scope in the acceptance criteria; an unbounded verifier is a token leak, not extra rigor.

**Tier 2 — scoped self-verification (same session).** For analysis scripts, plotting, plumbing, configs, and UI: (a) determinism check — run twice, artifacts byte-identical; (b) recompute one value independently from raw data (different code path, not a re-run); (c) UI/server changes additionally get a real browser pass (Claude_Preview MCP: load, click, read console) — API-only checks miss real UI bugs. No fresh agent.

**Tier 3 — no verification.** Docs, designs, comments. Review by reading.

**Hardware coverage is part of the pass (non-negotiable).** A pass certifies ONLY the (device, dtype) profiles it executed. A cpu/fp32 pass says nothing about the cuda path, and a ROCm pass says nothing about the DirectML backend (that gap is exactly what Back-verification Task 2 exists to close). If the change touches GPU code, the pass MUST include at least one real cuda execution and name every profile run. "PASS (cpu/fp32 only; cuda untested)" is the honest form.

## Rule 9 — adversarial review (claim time)
Before any result-bearing artifact is final (e.g. `verify/ACSL_AUDIT.md`, `FINDINGS.md`), a **fresh session with no access to this one** reviews the artifacts adversarially (an agent will not honestly attack its own work): argue the null/artifact explanation FIRST; verify controls/baselines were actually run at reported N; reproduce ≥1 headline number; banned celebration vocabulary; mandatory "Strongest case against this result" with ≥3 attack vectors; name ≥1 confound the design omits. Output → `verify/REDTEAM.md`, read by Matt BEFORE the implementing summary. Rule 9 applies to CLAIMS, not to every task — routine work uses the verification tiers above.

## Binding rules (audit floor — condensed from `~/Projects/memprobe/SPEC.md` §1; spec wins on conflict)
- No mocked/placeholder data in any results artifact. Synthetic data only under `tests/`.
- Every reported number regenerable by one command from files on disk. Summaries link the artifact path next to every number.
- Seeds everywhere; two runs = identical outputs. **N is sacred** — shortfalls are halted-and-reported, never silently absorbed.
- **You do not interpret results.** Present artifacts and plain factual summaries; Matt interprets.
- Any shortcut taken is recorded in the manifest `shortcuts_taken` field. An empty field is a claim.
- **Never auto-select layers from sweep results.** Present the table and let Matt choose.
- **This is defensive safety-evaluation research. Use only existing public benchmarks. Do not author novel jailbreaks or generate harmful content.**

## Known failure modes you are watched for
Fabricated numbers where a computation failed silently · evaluating on training data · silently reduced N · proxy metric reported under the original metric's name · heuristic classification reported as ground truth (the exact bug Back-verification Task 1 audits) · stale cached intermediates · loosened tolerances to make an assert pass · a verification pass that never executed the device/backend it certifies · narrating results as confirming what Matt wants to be true.

## Back-verification work order (the blocking mission)

### Task 1 — Refusal label audit
1. Locate the (prompt, model_output, refusal_label) triples in the ACSL data. Inventory first; report counts per label before building anything.
2. Build `verify/refusal_inspector` — single-file local HTML or Streamlit: one triple per screen, full prompt and output rendered, current label shown, keyboard-speed Accept/Reject/Unsure (j/k/u), progress counter, decisions appended to `verify/audit_decisions.jsonl` (timestamped).
3. Sampling plan (pre-registered, do not improvise): 200 triples, stratified by (a) refusal label × (b) probe-score quartile, seeded, seed recorded. If a stratum falls short, take all of it and report the shortfall.
4. **Matt performs the audit — not you.** Your job ends at presenting the tool and the sample.
5. After his pass: classifier error rate overall and per stratum with 95% CIs (Wilson). Recompute headline metrics (AUROC per layer, invariant band, hard-tail deltas) under corrected labels for the audited sample; report which findings move outside their original CIs.
6. Deliverable: `verify/ACSL_AUDIT.md` — factual, no adjectives, every number traceable to a file on disk.

### Task 2 — Backend cross-check (DirectML debt)
1. Select 10 ACSL prompts spanning the harm/actionability grid (seeded).
2. Re-run activation extraction on this stack (same model checkpoints — Qwen3-1.7B/4B — same tokenizer version; record both versions).
3. Compare per-layer residual activations against archived DirectML-era activations in `runs/`; if raw activations weren't archived, compare derived probe inputs/scores instead — and say so plainly.
4. Report max abs diff and rel diff per layer. Expectation: fp32-vs-fp32 ≈ 1e-5; fp32-vs-fp16 ≈ 1e-3. Anything worse is a finding, not a footnote.
5. Deliverable: appended section in `verify/ACSL_AUDIT.md`.
